# ออกแบบระบบเช็คชื่อเข้าเรียนแล็บด้วยการสแกนใบหน้า (Lab Attendance System)

## 1. ภาพรวมและเป้าหมาย

ระบบนี้ออกแบบมาเพื่อ:

1. เช็คชื่อนักศึกษาเข้าเรียนแต่ละแล็บ
2. เช็คชื่อด้วยการสแกนใบหน้า (รองรับการอัปเกรดเป็น Biometric Scan ในอนาคต)
3. มีโครงสร้างการเซ็นชื่อ/บันทึกที่เป็นมาตรฐาน ตรวจสอบย้อนหลังได้
4. ทำงานร่วมกับระบบตารางเรียนแล็บที่มีอยู่แล้วของแต่ละเทอม
5. สรุปผลการเข้าเรียน/ขาดเรียนได้ทั้งรายบุคคลและรายกลุ่ม
6. สร้างและดาวน์โหลดรายชื่อนักศึกษาแบ่งตามกลุ่มเรียนได้ทุกปีการศึกษา
7. จำกัดพื้นที่การสแกนด้วยการปักหมุด + กำหนดรัศมี เพื่อป้องกันการโกง (เช็คชื่อแทนกันจากนอกห้อง)

> **เพิ่มเติมภายหลัง**: ระบบจองห้องแล็บ (Room Booking) — ออกแบบใหม่ในระบบนี้ **เฉพาะการใช้ห้องเพื่อการเรียนแล็บ** (ตารางเรียนปกติ + ซ่อม/นัดพิเศษ) เป้าหมายหลักคือให้รู้ว่าคาบเรียนนี้อยู่ห้อง/ตึกไหน เพื่อกำหนดโซนสแกนหน้าให้แคบและตรงจุด (มหาวิทยาลัยมีหลายตึก) ส่วนการจองห้องเพื่อวัตถุประสงค์อื่นไม่อยู่ในขอบเขตนี้ (รายละเอียดหัวข้อ 3.3 และ 4.5)

**Actors หลักในระบบ**

| บทบาท | หน้าที่ |
|---|---|
| นักศึกษา | สแกนใบหน้าเพื่อเช็คชื่อผ่าน**มือถือเป็นหลัก** (เว็บแอป PWA) |
| อาจารย์ / TA ประจำแล็บ | ดูรายชื่อเข้าเรียนแบบเรียลไทม์, เช็คชื่อมือกรณีระบบมีปัญหา, **อนุมัติคำขอจองห้อง (class_schedule/makeup) ของแล็บตัวเอง** |
| เจ้าหน้าที่ทะเบียน / แอดมิน | **ตั้งค่าห้อง/พิกัด+รัศมี (กำหนดโซนสแกน)**, จัดการกลุ่มเรียน, ดึงรายงานสรุป, ดาวน์โหลดรายชื่อประจำปี |

## 2. สถาปัตยกรรมระบบ (Architecture)

แบ่งเป็น 5 ส่วนหลัก ทำงานแบบ loosely-coupled เพื่อให้ดูแลรักษาและขยายง่าย:

- **เว็บแอป (PWA) — นักศึกษา** (ปรับจาก Native App) — เข้าผ่านเบราว์เซอร์ ติดตั้งเป็นไอคอนบนหน้าจอหลักได้โดยไม่ต้องผ่าน App Store/Play Store (ไม่มีค่าธรรมเนียมนักพัฒนา) ขอสิทธิ์ GPS (`navigator.geolocation`) + กล้อง (`getUserMedia`) ผ่าน API มาตรฐานของเบราว์เซอร์ซึ่งฟรีทั้งคู่ หน้าตาคล้ายเว็บติดตามสถานะทั่วไป: เปิดลิงก์ → เห็นสถานะ → เช็คชื่อ
- **Backend API / Core Service** — จุดศูนย์กลางตรวจสอบสิทธิ์, ตำแหน่ง, จับคู่ embedding ใบหน้า, บันทึกผล
- **Room Booking Service** (ใหม่ — ขอบเขตเฉพาะการเรียนแล็บ) — จัดการห้องสำหรับ 2 กรณีเท่านั้น: (1) ตารางเรียนปกติของแต่ละกลุ่ม และ (2) ซ่อม/นัดพิเศษ ตรวจสอบห้องว่างกันชนกัน, generate รายการใช้ห้องจริงลง `schedules` **เป้าหมายหลักคือให้ระบบรู้ว่าคาบเรียนนี้ใช้ห้องไหน (ตึกไหน) เพื่อเลือกโซนสแกนใบหน้า (`locations`) ที่แคบและตรงจุด แทนการตั้ง geofence กว้างครอบคลุมทั้งมหาวิทยาลัยที่มีหลายตึก** — การจองห้องเพื่อวัตถุประสงค์อื่น (เช่น ใช้ทำโปรเจกต์ส่วนตัว) **ไม่อยู่ในขอบเขตของระบบนี้** ถ้ามีความต้องการควรแยกเป็นระบบต่างหากที่ไม่เกี่ยวข้องกับ check-in
- **Face Recognition — ทำงานฝั่ง Client (ในเบราว์เซอร์)** (ปรับจาก cloud API) — คำนวณ face embedding ในเครื่องนักศึกษาด้วยไลบรารีโอเพนซอร์สฟรี **Human library** (ตัวต่อยอดของ face-api.js ที่ยังพัฒนาต่อเนื่อง มี Face ID ในตัว — ดูเหตุผลในหัวข้อ 6) ไม่มีค่าใช้จ่ายต่อการสแกนแม้แต่บาทเดียว, เร็วกว่าเพราะไม่ต้องอัปโหลดรูปภาพ, และไม่ต้องส่งภาพใบหน้าออกจากเครื่อง (ส่งแค่ embedding vector ไป backend เพื่อจับคู่) — ดีต่อทั้งต้นทุนและความเป็นส่วนตัว
- **ฐานข้อมูล (Database)** — เก็บข้อมูลนักศึกษา, การจองห้อง/ตารางเรียน, บันทึกการเข้าเรียน
- **Course/Section Admin Management** (ปรับจาก Schedule Integration Layer) — ระบบตารางเรียนแล็บภายนอกที่คุยกันไว้ตอนแรก**ยังไม่มีอยู่จริง เป็นแค่แผนที่คิดไว้** จึงตัดตัวเชื่อม REST API/webhook ที่ซับซ้อนออก แทนที่ด้วยหน้าแอดมินธรรมดาให้กรอกข้อมูลวิชา/กลุ่มเรียน/อาจารย์ผู้สอนตรงในระบบนี้เลย (`courses`, `semesters`, `lab_sections` เป็นตารางภายในของระบบอยู่แล้ว ไม่ต้องรื้อ schema) เผื่ออนาคตมีระบบภายนอกจริงค่อยเพิ่มตัว sync ทีหลังได้
- **เว็บแอดมิน/อาจารย์** — ดูรายงาน (คล้ายหน้าสถานะแบบ real-time), อนุมัติ/จัดการคำขอจองห้อง, ตั้งค่าห้อง/พิกัด, ดาวน์โหลดรายชื่อ
- **LINE Notification Service** (ใหม่) — ส่งสรุปเข้าเรียนของแต่ละแล็บ/คาบไปยังกลุ่ม LINE OA อัตโนมัติ 2 ครั้งต่อคาบ (ครบ 15 นาที + จบคาบ) ใช้ **LINE Messaging API** ผ่าน LINE Official Account (**ไม่ใช่ LINE Notify ซึ่งยุติให้บริการไปแล้วตั้งแต่ 31 มีนาคม 2025**)
- **Google Drive Export Service** (ใหม่) — ใช้ Google Drive Pro ที่มีอยู่แล้วเป็นที่เก็บ**ไฟล์รายชื่อประจำปี**และ**backup ข้อมูลเข้าเรียน**เท่านั้น (ความถี่ต่ำ ปีละ/เทอมละไม่กี่ครั้ง) **ไม่ใช้เป็นฐานข้อมูลหลัก** — ฐานข้อมูลเชิงสัมพันธ์ยังจำเป็นสำหรับข้อมูลที่เขียนถี่อย่างเช็คชื่อ เพราะ Google Sheets API จำกัด write request ไว้แค่ 300 ครั้ง/นาทีต่อโปรเจกต์ และ 60 ครั้ง/นาทีต่อผู้ใช้ (ถ้าใช้ service account เดียวเขียนแทนทั้งระบบ จะเหลือแค่ 60 ครั้ง/นาทีจริงสำหรับทั้งมหาวิทยาลัย) ไม่พอสำหรับ event ที่เกิดถี่แบบนี้
- **Frontend Hosting: Cloudflare Pages** (ใหม่) — เก็บไฟล์ static ของเว็บแอป PWA ไม่ใช้ Vercel เพราะแผนฟรีของ Vercel จำกัดเฉพาะการใช้งานส่วนตัวไม่ใช่องค์กร ซึ่งระบบของมหาวิทยาลัยอยู่ในเขตก้ำกึ่งที่เสี่ยงผิดเงื่อนไข Cloudflare Pages free tier อนุญาตการใช้งานเชิงองค์กรได้ตรงๆ ไม่มีข้อจำกัดนี้

> **หมายเหตุเรื่องต้นทุน**: การเลือก PWA + client-side face recognition ทำให้ระบบนี้แทบไม่มีค่าใช้จ่ายด้าน license/API เลย ค่าใช้จ่ายที่เหลือคือ hosting backend/database เท่านั้น แนะนำ **Supabase free tier** เป็น backend + **Cloudflare Pages** เป็น frontend hosting (ดูรายละเอียดหัวข้อ 6) — เพียงพอสำหรับ pilot ระดับคณะ/มหาวิทยาลัยในช่วงแรก — ควรตรวจสอบเงื่อนไข free-tier ปัจจุบันก่อนผูกระบบจริง เพราะเปลี่ยนแปลงได้เรื่อยๆ
>
> **หมายเหตุเรื่อง LINE OA**: การส่งข้อความสรุปแบบอัตโนมัติ (ระบบเป็นฝ่ายเริ่มส่งเอง) จัดเป็น **push message** ซึ่งเสียโควต้ารายเดือนของแผน (ต่างจากการตอบกลับ webhook ที่ฟรีไม่จำกัด) แผนฟรีของ LINE OA ในไทยปัจจุบันให้โควต้าประมาณ 500 ข้อความ/เดือน (ตัวเลขนี้ LINE ปรับเปลี่ยนได้ ควรเช็คหน้าราคาทางการก่อนวางแผนจริง) การส่งเข้ากลุ่ม LINE นับเป็น 1 ข้อความต่อการส่ง 1 ครั้งไม่ว่ากลุ่มจะมีสมาชิกกี่คน ควรคำนวณปริมาณข้อความที่จะส่งจริง (จำนวนกลุ่มเรียน × จำนวนคาบ/สัปดาห์ × 2 ข้อความ/คาบ) เทียบกับโควต้าก่อนตัดสินใจว่าฟรีเพียงพอหรือต้องอัปเกรดแผน — **ถ้าเกินโควต้าในอนาคต แนะนำอัปเกรดแผน Light ของ LINE OA** (ถูกกว่าย้ายไป Facebook Fanpage หรือสร้างแอปแยกลง Play Store ซึ่งทั้งสองทางไม่ได้แก้ปัญหาจริงและเสียความคุ้นเคยของผู้ใช้) ทางเลือกสำรองแบบไม่มีโควต้าเลยคือเสริม Web Push API ผ่าน PWA เว็บแอดมินที่มีอยู่แล้ว
>
> **ข้อควรทดสอบก่อนใช้จริง**: Safari บน iOS รองรับกล้อง/GPS ผ่านเว็บได้ปกติ แต่พฤติกรรมการติดตั้งเป็นแอป (Add to Home Screen) และการขอสิทธิ์บางอย่างต่างจาก Android เล็กน้อย ควรทดสอบบนอุปกรณ์จริงทั้งสองแพลตฟอร์ม

**แนวทางการเชื่อมต่อกับระบบตารางเรียน (ข้อ 4)** มี 3 ทางเลือก:

| แนวทาง | ข้อดี | ข้อเสีย |
|---|---|---|
| A. REST API sync เป็นรอบ (เช่น ทุกคืน) | แยกระบบชัดเจน ปลอดภัย | ข้อมูลอาจไม่ real-time ถ้าตารางเปลี่ยนกะทันหัน |
| B. Webhook แจ้งเมื่อมีการแก้ตาราง | ข้อมูล real-time | ต้องพัฒนาทั้งสองฝั่งให้รองรับ webhook |
| C. Shared database / view ร่วมกัน | ง่ายสุดตอนแรก | ผูกติดกันแน่นมาก เปลี่ยนสคีมาฝั่งใดฝั่งหนึ่งกระทบอีกฝั่งทันที |

แนะนำ **A + B ผสมกัน**: sync หลักเป็นรอบ และเสริมด้วย webhook แจ้งเตือนเมื่อมีการแก้ไขตารางกะทันหัน (ยกเลิกคาบ, ย้ายห้อง)

## 4. ขั้นตอนการทำงานหลัก (Workflows)

### 4.1 การลงทะเบียนใบหน้า (Enrollment) — ทำครั้งเดียวตอนต้นเทอม/ต้นปี
1. นักศึกษายืนยันตัวตนครั้งแรก (เช่น ผ่าน SSO ของมหาวิทยาลัยที่มีอยู่แล้ว หรือกรอกรหัสนักศึกษาที่แอดมินสร้างไว้ล่วงหน้าใน `students`) — **ทำครั้งเดียวตอนลงทะเบียนเท่านั้น ไม่ใช่ทุกครั้งที่เช็คชื่อ**
2. ยืนยันความยินยอม (consent) ในการเก็บข้อมูลชีวมาตร
3. ถ่ายภาพใบหน้าหลายมุม → ระบบสร้าง embedding → เข้ารหัสและบันทึกลง `face_templates`

> **หลักการสำคัญ**: หลังลงทะเบียนแล้ว **ไม่มีการล็อกอินอีกเลยตลอดการใช้งาน** ใบหน้าคือตัวยืนยันตัวตนในตัวเอง ตอนเช็คชื่อ (4.2) ระบบจับคู่ embedding แบบ 1-to-N กับนักศึกษาทุกคนที่ลงทะเบียนไว้เพื่อหาว่าเป็นใคร ไม่ใช่ 1-to-1 กับคนที่ "ล็อกอินอยู่" — ทำให้ไม่ต้องมีหน้าจอกรอก username/password ระหว่างใช้งานจริงเลย

### 4.2 การเช็คชื่อ (Check-in) — ตามที่แสดงใน flow diagram ด้านบน

**ทางเข้าแอป (ใหม่) — QR Code ต่อห้อง**: แต่ละห้องมี QR แบบตายตัว (encode แค่ `location_id` ที่มีอยู่แล้วใน `locations` — ไม่ต้องเพิ่ม schema) พิมพ์ติดหน้าห้องได้เลย ไม่ต้องเปลี่ยนทุกคาบ นักศึกษาสแกนแล้วแอปเปิดตรงเข้าห้องนั้น ระบบเช็คเองว่าตอนนี้มีคาบอะไรอยู่ที่ห้องนี้ แล้วเข้าสู่ขั้นตอนปกติด้านล่างทันที — **QR ช่วยลดขั้นตอน "หาว่าต้องเปิดหน้าไหน" เท่านั้น ไม่ได้ข้ามการตรวจตำแหน่ง/สแกนหน้าเลย** ต่อให้มีคนถ่ายรูป QR ไปแชร์ คนที่ไม่ได้อยู่ในห้องจริงก็ยังเช็คชื่อไม่ผ่านเพราะ GPS ตรวจจับได้

1. ระบบตรวจสอบตารางเรียนปัจจุบันจาก `schedules` ว่าเวลานี้มีคาบอะไร กลุ่มไหน
2. ตรวจสอบตำแหน่ง GPS เทียบกับ `locations.radius_meters` — ถ้าอยู่นอกรัศมี **ปฏิเสธทันที** ก่อนเปิดกล้องด้วยซ้ำ (ประหยัดทรัพยากรและลดโอกาสส่งภาพจากนอกพื้นที่)

> **กรณีห้องใกล้กัน (GPS ชี้ห้องไม่ได้แม่นพอ)**: GPS แม่นยำจริงแค่ระดับ 5-20 เมตร (แย่กว่านั้นในอาคาร) ถ้าห้อง 2 ห้องอยู่ใกล้กันจนวงกลมรัศมีซ้อนทับกัน ให้แก้ตามลำดับนี้ ไม่ใช่พยายามบีบ GPS ให้แม่นขึ้น:
> 1. **ถ้าเข้าผ่าน QR ต่อห้อง (ทางเข้าหลักที่แนะนำ)** — รู้ห้องแน่นอนจาก `location_id` ที่ QR encode ไว้ทันที ไม่ต้องพึ่ง GPS เดาห้องเลย GPS เหลือหน้าที่แค่ sanity check ว่าไม่ได้อยู่ไกลเกินไป ปัญหานี้แทบไม่เกิดถ้าใช้ QR
> 2. **ถ้าไม่ได้ผ่าน QR และ GPS อยู่ในโซนซ้อนทับของหลายห้อง** — เช็ค `schedules` ของทุกห้องที่เป็นไปได้ ณ เวลานี้: ถ้ามีแค่ห้องเดียวที่มีคาบเรียนอยู่จริง ให้เลือกห้องนั้นอัตโนมัติโดยไม่ต้องถาม (แก้ปัญหาได้เงียบๆ ส่วนใหญ่)
> 3. **ถ้าหลายห้องมีคาบเรียนพร้อมกันจริงๆ (กำกวมแท้จริง)** — ค่อยให้นักศึกษาเลือกเองด้วยปุ่มสั้นๆ ("อยู่ห้อง 134 หรือ 135") เป็นทางเลือกสุดท้ายเท่านั้น เกิดขึ้นน้อยมากถ้าใช้ 2 ข้อแรกก่อน
> 4. **ไม่แนะนำ BLE beacon/WiFi fingerprint** แม้แม่นยำกว่า เพราะ Web Bluetooth ใช้ไม่ได้บน iOS Safari เลย จะดึงกลับไปมีปัญหา iOS ที่พยายามเลี่ยงไว้ตั้งแต่ต้น

3. สแกนใบหน้าและคำนวณ embedding **ในเบราว์เซอร์ฝั่งนักศึกษา** พร้อม liveness detection (ตรวจจับการกะพริบตา/ความลึกจาก landmark) กันการใช้รูปถ่ายสวมรอย
4. ส่งเฉพาะ embedding vector ไปยัง Backend เพื่อจับคู่แบบ **1-to-N กับนักศึกษาทุกคนที่ลงทะเบียนไว้ในระบบ** (ไม่ใช่ 1-to-1 กับคนที่ "ล็อกอินอยู่" เพราะไม่มีการล็อกอินระหว่างใช้งานจริง — ดู 4.1) หาคนที่คะแนนความเหมือนสูงสุด ถ้าต่ำกว่า threshold → ปฏิเสธ พร้อมแจ้งเหตุผล (รูปภาพจริงไม่ถูกส่งออกจากเครื่อง)
5. บันทึกผลลง `attendance_records` พร้อมสถานะ (ตรงเวลา/สาย เทียบกับ `schedules.start_time`)

**Fallback ที่ควรมี**: ถ้าเน็ตหลุดตอนสแกน ให้ทำ offline queue บนเครื่อง แล้ว sync เมื่อกลับมามีเน็ต และควรมีช่องทางให้อาจารย์/TA เช็คชื่อมือได้เสมอ (ถ้านักศึกษาไม่ยอมเปิดแอปหรือมีปัญหาทางเทคนิคจริง อาจารย์เห็นตัวอยู่ในห้องก็กดเช็คชื่อแทนได้จากเว็บแอดมิน) เพื่อไม่ให้ปัญหาทางเทคนิคหรือความไม่ร่วมมือกันนักศึกษาที่มาเรียนจริงออกจากระบบ

### 4.5 การจองห้องแล็บ (Room Booking) — ใหม่ เฉพาะการเรียนแล็บ

**เป้าหมายหลัก**: ให้ระบบรู้แน่ชัดว่าคาบเรียนนี้ใช้ห้องไหน (ตึกไหน) เพื่อดึงพิกัด+รัศมีของห้องนั้นมาใช้ตรวจสอบ GPS ตอนเช็คชื่อ — ทำให้โซนสแกนแคบและตรงจุดต่อคาบเรียน แทนที่จะตั้ง geofence กว้างครอบคลุมทั้งมหาวิทยาลัยที่มีหลายตึก (ดู diagram ด้านบน)

**ขอบเขต**: จัดการเฉพาะการใช้ห้องเพื่อการเรียนแล็บ 2 แบบ

| ประเภท | ใครขอ | การอนุมัติ | ผลลัพธ์ |
|---|---|---|---|
| class_schedule | อาจารย์เจ้าของแล็บ ต้นเทอม | **อาจารย์เจ้าของแล็บอนุมัติเอง** (ระบบตรวจสอบห้องว่างให้ก่อนแสดงผล กันชนกับ section อื่น) | generate `schedules` รายสัปดาห์ตลอดเทอม ผูกกับ `lab_sections` — ใช้เช็คชื่อได้ |
| makeup | อาจารย์เจ้าของแล็บ ระหว่างเทอม (ซ่อมแล็บ/นัดพิเศษ) | **อาจารย์เจ้าของแล็บอนุมัติเอง** (ระบบตรวจสอบห้องว่างให้ก่อน) | generate `schedules` แถวเดียว ผูกกับ section เดิม — ใช้เช็คชื่อได้ |

> **การจองห้องเพื่อวัตถุประสงค์อื่น** (เช่น นักศึกษา/อาจารย์ขอใช้ห้องทำโปรเจกต์ส่วนตัว) **ไม่อยู่ในขอบเขตของระบบนี้** — ไม่เกี่ยวข้องกับ check-in และไม่ต้อง generate เข้า `schedules` หากมีความต้องการควรใช้ระบบจองห้องแยกต่างหาก

**ขั้นตอนหลัก**:
1. รับคำขอจอง (ห้อง + วันเวลา + ประเภท + กลุ่มเรียน)
2. ตรวจสอบห้องว่าง — เทียบกับ `schedules`/`room_bookings` ที่อนุมัติแล้วในห้องและช่วงเวลาเดียวกัน ถ้าชนกันปฏิเสธทันที
3. ถ้าห้องว่าง ส่งให้**อาจารย์เจ้าของแล็บ**อนุมัติเอง (ทั้ง class_schedule และ makeup) ไม่ต้องผ่านแอดมินกลาง
4. เมื่ออนุมัติแล้ว generate แถวจริงลง `schedules` พร้อม `location_id` (booking แบบรายสัปดาห์จะ generate หลายแถวตลอดเทอม)
5. ห้องพร้อมใช้งานตามเวลาที่จอง — เปิดให้เช็คชื่อผ่าน flow เดิม โดยระบบดึง `locations` ของห้องที่ผูกไว้มาใช้กำหนดโซนสแกนอัตโนมัติ

**ข้อควรพิจารณาเพิ่มเติม**:
- แจ้งเตือน (notification) เมื่อคำขอ pending นานเกินกำหนด หรือเมื่อถูกอนุมัติ/ปฏิเสธ
- กรณี class_schedule ชนกับคำขอ makeup ที่จองไว้ก่อน (ต่างวิชากัน) ต้องมีทางแจ้งอาจารย์ทั้งสองฝ่ายตัดสินใจร่วมกัน (ย้ายห้อง/ย้ายเวลา) เนื่องจากไม่มีแอดมินกลางเป็นคนกลาง
- ถ้าตึกเดียวกันมีหลายห้องติดกัน ควรตั้งรัศมีให้แคบพอที่จะแยกห้องข้างเคียงออกจากกันได้ ไม่ใช่แค่แยกตึก

### 4.6 ระบบแจ้งเตือนทุกกิจกรรม (Notification Matrix) — ใหม่

**เป้าหมาย**: ครอบคลุมทุกกิจกรรมในระบบที่ต้องแจ้งเตือน ไม่ใช่แค่สรุปเข้าเรียน — จับคู่แต่ละกิจกรรมกับช่องทางที่เหมาะสมตามผู้รับและปริมาณ

**หลักการเลือกช่องทาง**: LINE ถูกเมื่อส่ง**เข้ากลุ่ม** (นับ 1 ข้อความ/กลุ่มไม่ว่ามีกี่คน) แต่จะแพงทันทีถ้าส่ง**หารายคนจำนวนมาก** (นับตามหัวคนจริง) — กิจกรรมที่ส่งหานักศึกษาทีละคนจำนวนมากจึงต้องใช้ Web Push เป็นหลักเท่านั้น

| กิจกรรม | ผู้รับ | ความถี่ | ช่องทาง | เหตุผล |
|---|---|---|---|---|
| สรุปเข้าเรียน (15 นาที + จบคาบ) | อาจารย์/แอดมิน (กลุ่ม) | สูง แต่นับต่อกลุ่ม | LINE + Web Push | ปริมาณต่ำเพราะนับต่อกลุ่มเรียนไม่ใช่ต่อคน |
| คำขอจองห้อง (`booking_submitted`) | อาจารย์เจ้าของแล็บ (รายคน) | ต่ำมาก | LINE + Web Push | ปริมาณน้อย ไม่กระทบโควต้า |
| ผลอนุมัติ/ปฏิเสธจองห้อง (`booking_approved`/`rejected`) | ผู้ขอจอง (รายคน) | ต่ำมาก | LINE + Web Push | เช่นเดียวกัน |
| รายชื่อประจำปีพร้อมดาวน์โหลด (`roster_ready`) | แอดมิน | ต่ำมาก (ปีละไม่กี่ครั้ง) | LINE หรือ Email | ไม่กระทบโควต้าเลย |
| เตือนคาบเรียนใกล้เริ่ม (`class_reminder`) — **ยืนยันแล้ว** | **นักศึกษาทีละคน** | **สูงมาก — ต่อคน × ต่อคาบ** | **Web Push เท่านั้น** | ถ้าใช้ LINE จะเสียโควต้าตามหัวคนจริง ไม่ใช่ตามกลุ่ม เสี่ยงชนโควต้าเร็วมากเมื่อสเกลขึ้น |

> **`class_reminder` (ยืนยันแล้ว — เป็นฟีเจอร์จริงของระบบ)**: เตือนนักศึกษาก่อนถึงคาบเรียน ใช้ **Web Push เป็นหลักเท่านั้น** ห้ามใช้ LINE (เหตุผลเรื่องโควต้าด้านบน)
> - **ผู้รับ**: นักศึกษาทุกคนใน `section_enrollments` ของ section นั้นที่มี `push_subscriptions.is_active = true` (คนที่ไม่ได้กดอนุญาตแจ้งเตือนจะไม่ได้รับ แต่เช็คชื่อได้ปกติผ่านลิงก์ตรง ไม่กระทบฟังก์ชันหลัก)
> - **เวลาส่ง**: `schedule.start_time` ลบ 10 นาที (ตั้งเป็นค่าเริ่มต้น ปรับได้ภายหลัง) — ใช้ job scheduler เดียวกับหัวข้ออื่นในตารางนี้ (ตรวจทุก 1 นาที)
> - **ตัวอย่างข้อความ**: "คาบ CPH64-242 LAB1 เริ่มในอีก 10 นาที ห้อง 134 อาคาร B8 อย่าลืมเช็คชื่อ"
> - นักศึกษาที่ยังไม่ได้ติดตั้ง PWA ไว้ที่หน้าจอหลัก (โดยเฉพาะ iOS ที่ต้องติดตั้งก่อนถึงจะรับ push ได้) จะไม่ได้รับการเตือนล่วงหน้า — ควรชวนติดตั้ง PWA ไว้ที่หน้าจอหลักตั้งแต่ขั้นตอนลงทะเบียนใบหน้าครั้งแรก เพื่อให้ครอบคลุมมากที่สุด

**เทคโนโลยีช่องทาง**:

> **ข้อสำคัญ**: ต้องสร้าง **LINE OA บัญชีใหม่แยกเฉพาะระบบนี้** ห้ามใช้บัญชีเดิมของคณะ/มหาวิทยาลัยที่มีอยู่แล้ว (เช่น บัญชีประชาสัมพันธ์ทั่วไป) เพราะแต่ละ LINE OA มีโควต้าข้อความแยกเป็นเอกเทศ ไม่แชร์กันข้ามบัญชี — ถ้าใช้ร่วมกับระบบอื่นจะเสี่ยงโดนแย่งโควต้าเวลามีการ broadcast จากงานอื่น แถมต้องประสานเรื่อง webhook endpoint กับทีมที่ดูแลบัญชีเดิมด้วย สร้างบัญชีใหม่ได้ฟรีและได้โควต้าฟรีเต็มจำนวนเป็นของระบบนี้เอง ส่วน Web Push ไม่มีความเสี่ยงนี้เลยเพราะผูกกับโดเมนเว็บแอปของเราเองผ่าน VAPID keys ของเราเอง ไม่มีแนวคิดบัญชี/โควต้าที่แชร์กันแบบ LINE
- **LINE Messaging API** ผ่าน LINE Official Account — **ไม่ใช่ LINE Notify** ซึ่งยุติให้บริการไปแล้วตั้งแต่ 31 มีนาคม 2025 การส่งข้อความแบบนี้เป็น push message ซึ่งเสียโควต้ารายเดือนของแผน แต่**การส่งเข้ากลุ่ม LINE นับเป็น 1 ข้อความต่อการส่ง 1 ครั้ง ไม่ว่ากลุ่มจะมีสมาชิกกี่คน** — ใช้ได้ดี**เฉพาะกิจกรรมที่ส่งเข้ากลุ่มหรือส่งหารายคนจำนวนน้อย**เท่านั้น ไม่เหมาะกับกิจกรรมที่ส่งหานักศึกษาทีละคนจำนวนมาก (ดูตารางด้านบน) — ถ้าเกินโควต้าในอนาคต แนะนำอัปเกรดแผน Light ของ LINE OA — ทั้งนี้ LINE เป็นแอป native จริง เชื่อมกับ APNs ของ Apple โดยตรง จึงแจ้งเตือนได้ปกติบน iOS ทุกกรณีโดยไม่มีเงื่อนไขพิเศษ
- **Web Push API** ผ่าน PWA ที่มีอยู่แล้ว (ทั้งฝั่งอาจารย์/แอดมิน และฝั่งนักศึกษา) — **ไม่มีโควต้าเลย ไม่มีค่าใช้จ่ายเลยไม่ว่าจะส่งกี่ข้อความ** เพราะใช้โครงสร้างพื้นฐานฟรีของเบราว์เซอร์ (Google/Apple/Mozilla) โดยตรง ต้องมี Service Worker + VAPID keys + ตาราง `push_subscriptions` (ผู้ใช้กดอนุญาตครั้งเดียว ใช้ได้ทั้งอาจารย์และนักศึกษาเพราะ FK ไปที่ `users` อยู่แล้ว) — iOS ต้องเป็น 16.4+ และติดตั้ง PWA ไว้ที่หน้าจอหลักก่อนถึงจะรับ push ได้ (แท็บ Safari ปกติใช้ไม่ได้) นี่คือช่องทางเดียวที่มีเงื่อนไขพิเศษบน iOS แต่แลกมากับการไม่มีโควต้าเลย

ทุกกิจกรรมในตารางส่งได้หลายช่องทางพร้อมกันในหนึ่ง job เดียวกัน (ไม่เพิ่มต้นทุนของ LINE แม้แต่บาทเดียวจากการเพิ่ม Web Push) บันทึกแยกแถวใน `notification_logs`

**นโยบายเวลาส่งของสรุปเข้าเรียน — 2 ครั้งต่อคาบ**:

## 5. การป้องกันการโกง (Anti-fraud)

| มาตรการ | รายละเอียด |
|---|---|
| Geofencing | ปักหมุด + กำหนดรัศมีต่อห้อง (`locations` table) ตรวจสอบก่อนอนุญาตสแกนหน้า |

## 6. เทคโนโลยีที่แนะนำพิจารณา (สรุปสั้น — เน้นฟรีและมีประสิทธิภาพ)

- **Face Recognition**: **Human library** (`@vladmandic/human`) — ตัวต่อยอดของ face-api.js โดยผู้พัฒนาคนเดิม (face-api.js ทั้งต้นฉบับและ fork ถูก archive แล้ว ไม่แนะนำใช้ต่อสำหรับงานจริง) มีฟีเจอร์ **Face ID** ในตัวที่รวม liveness detection + จับคู่ใบหน้ากับฐานข้อมูลในขั้นตอนเดียว รองรับโมเดล mobilefacenet ที่ออกแบบมาสำหรับมือถือโดยเฉพาะ ปรับสมดุลคุณภาพ/ประสิทธิภาพอัตโนมัติตามเครื่อง — โหลดผ่าน jsdelivr แบบ npm-mirror มาตรฐาน เชื่อถือได้กว่า path ที่พึ่ง GitHub repo ตรงๆ **MediaPipe Face Landmarker** ยังคงเป็นตัวเลือกที่ดีที่สุดถ้าต้องการแค่ detection/landmark ล้วนๆ (Google ดูแลต่อเนื่อง เบาแรง) แต่**ไม่มี identity recognition ในตัว** ต้องจับคู่กับโมเดลอื่นเพิ่มถ้าจะใช้ระบุตัวตน จึงไม่เหมาะเป็นตัวหลักของงานนี้ — **ยังต้อง benchmark Human บนมือถือรุ่นล่างจริงก่อนฟันธงขั้นสุดท้าย** แต่เป็นจุดเริ่มต้นที่ดีกว่า face-api.js เดิมชัดเจน
- **Geofencing**: `navigator.geolocation` ของเบราว์เซอร์ (ฟรี) คำนวณระยะทางด้วย Haversine formula ระหว่างพิกัดนักศึกษาและพิกัดห้อง
- **Frontend**: เว็บแอปแบบ PWA (React/Vue + Workbox สำหรับ offline/installable) โค้ดเดียวใช้ได้ทุกอุปกรณ์ผ่านเบราว์เซอร์ ไม่มีค่าธรรมเนียม App Store/Play Store
- **Backend**: REST API มาตรฐาน, ใช้ queue (เช่น RabbitMQ/SQS) สำหรับ sync ตารางเรียนแบบ async และ job scheduler สำหรับแจ้งเตือน LINE ตามเวลาคาบเรียน
- **แจ้งเตือน**: LINE Messaging API ผ่าน LINE Official Account (แผนฟรีมีโควต้าข้อความ/เดือน ควรคำนวณปริมาณการใช้จริงก่อนตัดสินใจ)
- **Hosting**: **Supabase free tier** (Postgres + Auth + Edge Functions) เป็น backend ทั้งหมด **pause อัตโนมัติหลังไม่มีการใช้งาน 7 วัน** (กระทบช่วงปิดเทอม) แก้ด้วยการรัน job แจ้งเตือน LINE (ข้อ 4.7) เป็น **Supabase Edge Function บน Supabase Cron** แทนที่จะหา cron แยกต่างหาก — ทุกครั้งที่ job รันทุก 1 นาทีจะแตะฐานข้อมูล ทำหน้าที่กัน pause ไปในตัว ไม่ต้องทำ keep-alive job แยก
- **Frontend Hosting**: **Cloudflare Pages** (ไม่ใช่ Vercel) — free tier ของ Cloudflare Pages อนุญาตการใช้งานเชิงองค์กรได้ตรงๆ ไม่มีข้อจำกัด ต่างจาก Vercel ที่แผนฟรี (Hobby) จำกัดเฉพาะการใช้งานส่วนตัวแบบไม่ใช่องค์กร/พาณิชย์ตามเงื่อนไขการใช้งาน — ระบบของมหาวิทยาลัยที่ใช้งานจริงทั้งคณะอยู่ในเขตก้ำกึ่งที่เสี่ยงต้องอัปเกรดเป็น Pro ($20/เดือน) ถ้าใช้ Vercel จริงจัง จึงเลือก Cloudflare Pages ซึ่งไม่มีข้อจำกัดนี้และรองรับไฟล์ static ของ PWA ได้ดีอยู่แล้ว
- **ทางเลือกอื่น**: Firebase Firestore free tier (Spark plan) ไม่มีปัญหา auto-pause เลย (ทำงานต่อเนื่องตลอด) แต่เป็น NoSQL ต้องออกแบบ schema ใหม่จากที่วางไว้เป็น relational ทั้งหมด — เหมาะถ้าเริ่มต้นใหม่ ไม่เหมาะถ้าจะใช้ schema ที่ออกแบบไว้แล้วในเอกสารนี้
- **ไฟล์รายชื่อ/Backup**: ใช้ Google Drive Pro ที่มีอยู่แล้ว ผ่าน Google Drive API — เหมาะกับไฟล์รายชื่อประจำปีและ backup ข้อมูลเข้าเรียนเป็นระยะ (เช่น จบเทอม) เพราะเป็นงานความถี่ต่ำ ไม่ใช่ที่เก็บข้อมูล check-in ซึ่งต้องเขียนถี่กว่าที่ Sheets/Drive API รองรับ

## 8. แผนอนาคต (ยังไม่ออกแบบ/ตัดออกไปก่อนตอนนี้)

- **ระบบสรุปต้นทุนวัสดุและครุภัณฑ์** — ผู้ใช้แจ้งว่าจะต้องทำงานร่วมกับระบบเช็คชื่อนี้ในอนาคต **เหตุผล**: การรู้จำนวนนักศึกษาที่เข้าเรียนจริง (`attendance_records.status`) แทนจำนวนที่ลงทะเบียนไว้ (`section_enrollments`) ทำให้คำนวณต้นทุนวัสดุ (สิ้นเปลืองต่อหัว) ได้แม่นยำขึ้น — ส่วนต้นทุนครุภัณฑ์ตามระยะเวลาใช้งานจริงจะต้องรอ Presence Tracking กลับมาก่อน (ดูข้อถัดไป) เพราะตอนนี้ไม่มี field ที่เก็บระยะเวลาอยู่จริงแล้ว ยังไม่ต้องออกแบบระบบต้นทุนตอนนี้ตามที่ผู้ใช้ขอให้คิดทีหลัง

- **Presence Tracking (ออกแบบไว้แล้ว — ตัดออกไปก่อนตามคำขอผู้ใช้)** — ฟีเจอร์ตรวจสอบว่านักศึกษาอยู่ในพื้นที่จริงอย่างน้อย 15-20 นาทีหลังเช็คชื่อ (กันเช็คชื่อแล้วหนีเรียน) ถูกออกแบบไว้ครบแล้วรวมถึงเวอร์ชันปรับปรุงที่ไม่ต้องบังคับเปิดจอ/แท็บค้างไว้ (ใช้ "Prompted Check-in" ผ่าน Web Push แทน Wake Lock API) แต่**ผู้ใช้ตัดสินใจตัดออกไปก่อน**เพื่อลดความซับซ้อนของ pilot รอบแรก ถ้าต้องการกลับมาทำในอนาคต จุดที่ต้องเพิ่มกลับเข้าไป:
  - ตาราง `presence_logs` ใหม่ (log การ ping ตำแหน่งเป็นระยะ)
  - field ใน `attendance_records`: `required_stay_minutes`, `presence_status`, `left_area_at`, `actual_duration_minutes`
  - `notification_type` เพิ่ม `left_area_alert` และ `presence_check`
  - workflow และเหตุผลทางเทคนิคทั้งหมด (ข้อจำกัด background location, ทำไมเลือก Prompted Check-in) มีบันทึกไว้ครบใน Context.md ของโปรเจกต์นี้แล้ว ไม่ต้องคิดใหม่ตั้งแต่ต้น
