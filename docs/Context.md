## 1. ความต้องการต้นฉบับของผู้ใช้ (Requirements)

ระบบต้อง:

1. เช็คชื่อนักศึกษาแต่ละแล็บเข้าเรียน
2. เช็คชื่อแบบสแกนหน้า (ถ้าเป็นไปได้ให้เป็น BIO Scan)
3. มีโครงสร้างตัวอย่างในการเซ็นชื่อ
4. ทำงานร่วมกับระบบลงตารางเรียนของแล็บแต่ละเทอม (**แก้ไขภายหลัง: ยังไม่มีระบบภายนอกจริง เป็นแค่แผนที่คิดไว้ตอนแรก** — ตัดสินใจให้จัดการวิชา/กลุ่มเรียน/อาจารย์ภายในระบบนี้เอง ไม่ต้องสร้างตัวเชื่อมภายนอก)
5. สรุปการเข้าเรียน/ขาดเรียนได้
6. ทุกปีมีรายชื่อให้ดาวน์โหลด แบ่งตามจำนวนกลุ่มเรียน (จำนวนกลุ่มไม่คงที่แต่ละปี)
7. สแกนหน้าได้เฉพาะพื้นที่ที่กำหนด (ปักหมุด + กำหนดรัศมี) เพื่อป้องกันการโกง
8. **(เพิ่มภายหลัง, ปรับขอบเขตแล้ว)** มีระบบจองห้องแล็บ — ออกแบบใหม่ในระบบนี้ **เฉพาะการใช้ห้องเพื่อการเรียนแล็บ** (ตารางเรียนปกติ + ซ่อม/นัดพิเศษ) เป้าหมายหลักคือรู้ว่าคาบเรียนนี้อยู่ห้อง/ตึกไหน เพื่อกำหนดโซนสแกนหน้าให้แคบ (มหาวิทยาลัยมีหลายตึก) — การจองห้องเพื่อวัตถุประสงค์อื่น **ไม่อยู่ในขอบเขตนี้**
9. **(เพิ่มภายหลัง)** ต้องคำนึงว่านักศึกษามือถือสเปกไม่สูง — เลือกโมเดล/วิธีประมวลผลที่เบาและทดสอบบนเครื่องจริง
10. **(เพิ่มภายหลัง)** เน้นความง่ายในการใช้งาน (UX) เป็นหลักสำคัญ
11. **(เพิ่มภายหลัง, ตัดออกจาก scope ปัจจุบันแล้ว)** หลังเช็คชื่อสำเร็จ ต้องอยู่ในพื้นที่อย่างน้อย 15-20 นาที ไม่งั้นบันทึกว่าออกนอกพื้นที่ระหว่างเรียน (Presence Tracking) — ออกแบบไว้ครบแล้ว รวมถึงเวอร์ชันปรับปรุงที่ไม่บังคับเปิดจอค้าง แต่ผู้ใช้ตัดสินใจตัดออกก่อนเพื่อลดความซับซ้อนของ pilot รอบแรก ดูรายละเอียดที่เก็บไว้ในหัวข้อ 8 ของ `lab-attendance-system-design.md`
12. **(เพิ่มภายหลัง)** ต้องทำงานร่วมกับ LINE OA เพื่อสรุปการเข้าเรียนแต่ละแล็บ/คาบ ส่งอัตโนมัติ 2 ครั้ง (ครบ 15 นาที + จบคาบ) รูปแบบข้อความ: รหัสวิชา, แล็บ, ชื่อบท, ห้อง+ตึก, เวลา, จำนวนปกติ/สาย/ขาด
13. **(เพิ่มภายหลัง, ยังไม่ออกแบบ)** ต้องทำงานร่วมกับระบบสรุปต้นทุนวัสดุและครุภัณฑ์ในอนาคต — ผู้ใช้ระบุชัดเจนว่า**ค่อยคิดทีหลัง** ตอนนี้แค่บันทึกไว้เป็นแผน ไม่ต้องออกแบบ
14. **(เพิ่มภายหลัง, ยืนยันแล้ว)** เตือนนักศึกษาก่อนถึงคาบเรียน (`class_reminder`) — ส่งก่อนคาบเริ่ม 10 นาที ผ่าน Web Push เท่านั้น (ไม่ใช้ LINE เพราะต้นทุนโควต้า)

## 2. การตัดสินใจสำคัญที่ทำไปแล้ว

**การแยกจากระบบเดิมในโปรเจกต์เดียวกัน (ประวัติ — แก้ไขแล้ว/obsolete)** — ระหว่าง deploy จริง เคยพบว่า "rov-system" ที่ใช้เป็นโปรเจกต์เดิมที่มีระบบ ROV (เกม) อยู่แล้ว ไม่ใช่โปรเจกต์ใหม่ และโควต้าโปรเจกต์ฟรีของบัญชีเต็มแล้ว (จำกัด 2 โปรเจกต์ต่อบัญชี นับรวมทุก organization ไม่ใช่แยกตาม org) จึงเคยแก้ชั่วคราวด้วยการสร้าง Postgres schema แยกชื่อ `lab_checkin` ภายในโปรเจกต์เดียวกัน — **ตอนนี้ obsolete แล้ว** เพราะพบและยืนยันว่ามีโปรเจกต์ **"cph-smart-checkin"** ที่สร้างแยกเฉพาะระบบนี้อยู่แล้วจริง จึงย้าย schema เต็ม + Edge Function ไปที่โปรเจกต์ใหม่นี้แทน กลับไปใช้ `public` schema ตามปกติ ไม่ต้องแยก schema อีกต่อไป (ไฟล์ `migration-002-separate-schema.sql` เก็บไว้เป็นประวัติเฉยๆ ไม่ต้องรันแล้ว)

**สถาปัตยกรรม** — แยกเป็น 5 ส่วน แบบ loosely-coupled:
- เว็บแอป (PWA, นักศึกษา) — GPS + กล้องผ่านเบราว์เซอร์ (ปรับจาก Native App)
- Backend API / Core Service — ตรวจสอบตำแหน่ง + จับคู่ embedding ใบหน้า + บันทึกผล
- Face Recognition — **ทำงานฝั่ง client (ในเบราว์เซอร์)** ด้วย MediaPipe Face Landmarker หรือ face-api.js (ปรับจาก cloud API)
- ฐานข้อมูล
- Course/Section Admin Management (ปรับจาก Schedule Integration Layer — ไม่มีระบบภายนอกจริง จึงเป็นแค่หน้าแอดมิน CRUD ภายในระบบนี้)
- เว็บแอดมิน/อาจารย์ — รายงาน + ดาวน์โหลดรายชื่อ

**เหตุผลการเปลี่ยนเป็น PWA + Client-side Face Recognition** — ผู้ใช้ต้องการเน้น**ฟรีและมีประสิทธิภาพดีที่สุด** และกังวลเรื่องค่าใช้จ่ายของแอปมือถือ (native app มีค่าธรรมเนียม App Store/Play Store) จึงปรับเป็น:
- PWA แทน Native App — ไม่มีค่าธรรมเนียม, โค้ดเดียวใช้ทุกอุปกรณ์, ติดตั้งผ่านเบราว์เซอร์ได้เลย
- Face embedding คำนวณในเบราว์เซอร์ฝั่งนักศึกษา แทน cloud Face API ที่คิดเงินต่อการสแกน — ไม่มีค่า API, เร็วกว่า, ส่งแค่ embedding vector ไป backend (ไม่ส่งรูปภาพ)
- ค่าใช้จ่ายที่เหลือคือ hosting backend/database เท่านั้น (Supabase free tier เป็น backend + Vercel เป็น frontend hosting — ดูหัวข้อ Hosting Stability ด้านล่าง)

**ข้อจำกัดอุปกรณ์และ UX (เพิ่มภายหลัง)** — นักศึกษาส่วนใหญ่ใช้มือถือสเปกไม่สูง ต้อง:
- ใช้โมเดล quantized/เบา, downscale ภาพก่อนประมวลผล, สแกนแบบภาพนิ่ง 1-2 เฟรมแทนวิดีโอต่อเนื่อง, lazy-load โมเดล ML
- **ต้อง benchmark บนมือถือรุ่นล่างจริงก่อนเลือกระหว่าง MediaPipe กับ face-api.js** (ยังไม่ฟันธง)
- เน้นความง่ายในการใช้งานเป็นหลัก: ขั้นตอนน้อยที่สุด, step indicator ชัดเจน, ข้อความภาษาไทยเข้าใจง่าย, ปุ่มใหญ่กดง่าย

**Presence Tracking — ตัดออกจาก scope ปัจจุบันแล้ว (ตัดสินใจล่าสุด)**: ออกแบบไว้ครบแล้วรวมถึงเวอร์ชันปรับปรุง "Prompted Check-in" ที่ไม่บังคับเปิดจอ/แท็บค้างไว้ (ใช้ Web Push แจ้งเตือนให้แตะยืนยันเป็นครั้งคราวแทน Wake Lock API ต่อเนื่อง) แต่ผู้ใช้ตัดสินใจตัดออกก่อนเพื่อลดความซับซ้อนของ pilot รอบแรก — รายละเอียดทั้งหมด (schema, เหตุผลข้อจำกัด background location, ทำไมเลือก Prompted Check-in) เก็บไว้ในหัวข้อ 8 ของ `lab-attendance-system-design.md` แล้ว ไม่ต้องคิดใหม่ถ้ากลับมาทำในอนาคต

**หลักการยืนยันตัวตน — ไม่มีล็อกอินแยก (ยืนยันแล้ว)** — ใบหน้าคือตัวยืนยันตัวตนในตัวเองอยู่แล้ว ไม่ต้องมีหน้า login/username-password แยกต่างหาก: ลงทะเบียนชื่อ-นามสกุล+รหัสนักศึกษาแค่ครั้งแรกครั้งเดียวคู่กับใบหน้า จากนั้นทุกครั้งที่เช็คชื่อแค่สแกนหน้าตรงๆ ระบบค้นหาคนที่ตรงที่สุดจากทุกคนที่ลงทะเบียนไว้ให้เอง (1-to-N matching) — Prototype ปรับให้รองรับหลายคนพร้อมกันแล้วเพื่อพิสูจน์หลักการนี้

**ห้องใกล้กัน (GPS กำกวม) — แก้แล้ว**: GPS แม่นจริงแค่ 5-20 เมตร (แย่กว่าในอาคาร) ถ้าห้อง 2 ห้องอยู่ใกล้กันจนวงกลมรัศมีซ้อนทับ แก้ด้วย 3 ชั้นเรียงลำดับ ไม่ใช่พยายามบีบ GPS ให้แม่นขึ้น:
1. **QR ต่อห้อง (ทางหลัก)** — รู้ห้องจาก `location_id` ที่ QR encode ไว้ตรงๆ ไม่ต้องพึ่ง GPS เดาห้องเลย
2. **บูรณาการกับตารางเรียน (ถ้าไม่ได้ผ่าน QR)** — ถ้า GPS อยู่ในโซนซ้อนทับ เช็ค `schedules` ของห้องที่เป็นไปได้ทั้งหมด ถ้ามีแค่ห้องเดียวที่มีคาบเรียนอยู่จริงตอนนี้ → auto-resolve เงียบๆ ไม่ต้องถาม
3. **ถามผู้ใช้เป็นทางเลือกสุดท้าย** — เฉพาะกรณีหลายห้องมีคาบพร้อมกันจริงๆ (กำกวมแท้) ค่อยโชว์ปุ่มเลือกสั้นๆ
- **พิจารณาแล้วไม่เลือก**: BLE beacon/WiFi fingerprint — แม่นกว่าแต่ Web Bluetooth ใช้ไม่ได้บน iOS Safari เลย จะดึงกลับไปมีปัญหา iOS ที่เลี่ยงไว้ตั้งแต่ต้น
- **แก้ bug ที่เจอระหว่างทาง**: `GET /checkin/current-session` เดิมออกแบบผิดให้อิงตัวนักศึกษา (แบบมี login) ซึ่งขัดกับโมเดล "ไม่มีล็อกอิน" ที่เพิ่งยืนยัน — แก้เป็นอิงตำแหน่ง (`location_id` จาก QR หรือ `lat`/`lng`) แทน คืนค่า `resolved: single` หรือ `resolved: ambiguous` (พร้อม `candidates` ให้เลือก) ตามกรณีข้างต้น

**การเชื่อมต่อกับระบบตารางเรียน (ข้อ 4)** — แนะนำ REST API sync เป็นรอบ + webhook แจ้งเตือนเมื่อมีการแก้ไขตารางกะทันหัน ไม่ใช้ shared database (กันผูกติดกันแน่นเกินไป)

**QR Code ต่อห้อง (เพิ่มภายหลัง — ตัดสินใจแล้ว)** — ตอบคำถาม "นักศึกษาไม่อยากเปิดแอปทำยังไง": 2 ชั้นป้องกัน
- **ชั้นที่ 1 (มีอยู่แล้วตั้งแต่ต้น)**: อาจารย์/TA เช็คชื่อมือได้เสมอจากเว็บแอดมิน ถ้านักศึกษาไม่ยอมเปิดแอปจริงๆ
- **ชั้นที่ 2 (ใหม่)**: QR code ตายตัวต่อห้อง (encode แค่ `location_id` ที่มีอยู่แล้ว ไม่ต้อง schema ใหม่) พิมพ์ติดหน้าห้องถาวร สแกนแล้วเปิดแอปตรงเข้าห้องนั้น ลด friction "หาว่าต้องเปิดหน้าไหน" **แต่ไม่ข้ามการตรวจตำแหน่ง/สแกนหน้าเลย** — ต่อให้แชร์รูป QR คนนอกห้องก็เช็คชื่อไม่ผ่านเพราะ GPS จับได้ จึงไม่กระทบความปลอดภัยของระบบ
- เพิ่มปุ่ม "ดู QR"/"ดาวน์โหลด" ในหน้าตั้งค่าห้องของเว็บแอดมินแล้ว (mockup)
- **พิจารณาแล้วไม่เลือก**: ให้ QR เป็นการเช็คชื่อเองเลย (ไม่ต้องสแกนหน้า) — ปฏิเสธเพราะทำลายจุดประสงค์หลักของทั้งระบบ (กันคนอื่นเช็คชื่อแทน)

**LINE OA Notification (เพิ่มภายหลัง — ตัดสินใจแล้ว)** — ใช้ **LINE Messaging API** ผ่าน LINE Official Account (**ไม่ใช่ LINE Notify ซึ่งยุติให้บริการไปแล้วตั้งแต่ 31 มีนาคม 2025**):
- **ต้องสร้าง LINE OA ใหม่แยกเฉพาะระบบนี้ ห้ามใช้บัญชีเดิมของคณะ/มหาวิทยาลัยที่มีอยู่แล้ว** — เหตุผล: แต่ละ LINE OA มีโควต้าแยกเป็นเอกเทศ ไม่แชร์กันข้ามบัญชี ถ้าใช้บัญชีเดิมร่วมกับระบบอื่น (เช่น ประชาสัมพันธ์ทั่วไป) จะเสี่ยงโดนแย่งโควต้าเวลาฝ่ายอื่น broadcast เยอะ แถมต้องประสานเรื่อง webhook endpoint ร่วมกับทีมที่ดูแลบัญชีเดิม สร้างใหม่ฟรีและได้โควต้าฟรีเต็ม ~500/เดือนเป็นของตัวเอง
- ส่งแจ้งเตือน **2 ครั้งต่อคาบ**: (1) ครบ `late_threshold_minutes` (ค่าเริ่มต้น 15 นาที) = สถานะระหว่างคาบ, (2) จบคาบ (`end_time`) = สรุปสุดท้าย ปกติ/สาย/ขาด
- **ขาดเรียน** = ไม่เช็คชื่อเลยจนจบคาบ เท่านั้น ไม่มี cutoff แยกต่างหาก
- ตาราง `line_channels` (map section → LINE group) และ `notification_logs` (log ข้อความที่ส่ง) เพิ่มเข้า schema แล้ว
- ต้องมี job scheduler ตรวจทุก ~1 นาทีว่าคาบไหนถึงจุดแจ้งเตือน
- **กลไกโควต้า (ยืนยันแล้ว)**: LINE OA เสียโควต้าเฉพาะ push message (ต่างจาก reply ที่ฟรี) แต่**การส่งเข้ากลุ่ม LINE นับเป็น 1 ข้อความต่อการส่ง 1 ครั้ง ไม่ว่ากลุ่มจะมีสมาชิกกี่คน** — โควต้าจึงขึ้นกับจำนวนกลุ่มเรียน × จำนวนคาบ ไม่ใช่จำนวนนักศึกษา ทำให้ใช้งานจริงต่ำกว่าที่กังวลไว้มาก (100 กลุ่มเรียน สัปดาห์ละครั้ง ×2 แจ้งเตือน ≈ 860 ข้อความ/เดือน)
- **แผนขยายสเกลในอนาคต (ตัดสินใจแล้ว)**: ถ้าเกินโควต้าฟรี (~500/เดือนในไทย) ให้**อัปเกรดเป็นแผน Light ของ LINE OA** (หลักพันบาท/เดือนสำหรับหลักพันข้อความ) — ถูกและง่ายกว่าทางเลือกอื่น **ไม่ย้ายไป Facebook Fanpage** (Meta มีนโยบายจำกัด proactive message คล้ายกัน ไม่ได้แก้ปัญหาจริง แถมคนไทยคุ้นเคย LINE มากกว่า) **ไม่สร้างแอปแยกลง Play Store** เพื่อแก้ปัญหานี้
- **Web Push API (ตัดสินใจแล้ว — เพิ่มเข้ามาจริง ไม่ใช่แค่สำรอง)**: ส่งคู่กับ LINE ทุกครั้งที่มีแจ้งเตือน ผ่าน PWA เว็บแอดมิน/อาจารย์ที่มีอยู่แล้ว **ไม่มีโควต้าเลย ไม่มีค่าใช้จ่ายเลยไม่ว่าส่งกี่ข้อความ** เพราะใช้โครงสร้างพื้นฐานฟรีของเบราว์เซอร์โดยตรง (ไม่ผ่านบริการที่มีค่าใช้จ่ายใดๆ) ต้องมี Service Worker + VAPID keys + ตาราง `push_subscriptions` ใหม่ — เพิ่มต้นทุนศูนย์บาทจากการมี LINE อยู่แล้ว ข้อจำกัด: iOS ต้องเป็น 16.4+ และอาจารย์ต้องติดตั้ง PWA ไว้ที่หน้าจอหลักก่อนถึงจะรับ push ได้
- **Notification Matrix ครอบคลุมทุกกิจกรรม (ตัดสินใจแล้ว)** — ขยายจากแค่ "สรุปเข้าเรียน" เป็นทุกกิจกรรมที่ต้องแจ้งเตือน: สรุปเข้าเรียน, คำขอ/ผลอนุมัติจองห้อง, รายชื่อพร้อมดาวน์โหลด (ทั้งหมดนี้ผ่าน LINE+Web Push เพราะส่งเข้ากลุ่มหรือส่งหารายคนจำนวนน้อย ปริมาณต่ำ) — **`class_reminder` (เตือนนักศึกษาก่อนถึงคาบเรียน) ยืนยันแล้วว่าเป็นฟีเจอร์จริงของระบบ** ไม่ใช่แค่ตัวเลือก: ส่งก่อนคาบเริ่ม 10 นาที (ค่าเริ่มต้น ปรับได้) หาทุกคนใน `section_enrollments` ที่มี active push subscription **ใช้ Web Push เท่านั้น ห้ามใช้ LINE** เพราะส่งหานักศึกษาทีละคนจำนวนมาก โควต้า LINE จะนับตามหัวคนจริง (ต่างจากกลุ่มเรียนที่นับ 1 ข้อความ/กลุ่ม) เสี่ยงชนโควต้าเร็วมาก — เรื่อง iOS ไม่ใช่ปัญหาของ LINE เลย (LINE เป็น native app เชื่อม APNs ของ Apple โดยตรง) แต่เป็นปัญหาของ Web Push เท่านั้น (ต้องติดตั้ง PWA ก่อนถึงจะรับได้บน iOS) — ควรชวนติดตั้ง PWA ตั้งแต่ขั้นตอนลงทะเบียนใบหน้าครั้งแรกเพื่อให้ครอบคลุมมากที่สุด (หมายเหตุ: เดิมมี `left_area_alert` ด้วย แต่ถูกตัดออกพร้อม Presence Tracking)

**แผนอนาคต (บันทึกไว้ ยังไม่ออกแบบ)** — ระบบสรุปต้นทุนวัสดุและครุภัณฑ์: **เหตุผลที่ต้องเชื่อมกัน** (ผู้ใช้อธิบายเพิ่ม) — จำนวนคนเข้าเรียนจริง (ไม่ใช่จำนวนลงทะเบียน) ทำให้คิดต้นทุนวัสดุต่อหัวได้แม่นยำขึ้น (ยังใช้ `attendance_records.status` ได้ปกติ) ส่วนต้นทุนครุภัณฑ์ตามระยะเวลาใช้งานจริงต้องรอ Presence Tracking กลับมาก่อน เพราะ field `actual_duration_minutes` ที่เคยเพิ่มไว้ถูกลบไปพร้อมกับการตัด Presence Tracking แล้ว — **ยังไม่ออกแบบระบบต้นทุนเอง** ตามที่ผู้ใช้ขอให้คิดทีหลัง

**Google Drive Pro (เพิ่มภายหลัง — ตัดสินใจแล้ว)** — ผู้ใช้มี Google Drive Pro อยู่แล้ว อยากใช้ประโยชน์ แต่ **Drive เป็นที่เก็บไฟล์ ไม่ใช่ relational database** จึงจำกัดขอบเขตการใช้ไว้เฉพาะ:
- ไฟล์รายชื่อประจำปี (ข้อ 6) — อัปโหลดผ่าน Google Drive API จัดโฟลเดอร์ตามปี/เทอม บันทึก `drive_file_id`/`drive_folder_path` ใน `rosters`
- Backup ข้อมูลเข้าเรียนเป็นระยะ (เช่น จบเทอม)
- **เหตุผลที่ไม่ใช้เป็นฐานข้อมูลหลัก**: Google Sheets API จำกัด write request 300 ครั้ง/นาทีต่อโปรเจกต์ และ 60 ครั้ง/นาทีต่อผู้ใช้ ถ้าใช้ service account เดียวเขียนแทนทั้งระบบ (วิธีมาตรฐาน) จะเหลือแค่ 60 ครั้ง/นาทีจริงสำหรับทั้งมหาวิทยาลัย ไม่พอสำหรับเช็คชื่อที่เกิดถี่ — ฐานข้อมูลเชิงสัมพันธ์ (Supabase/Firebase/ฯลฯ ที่เลือกไว้แล้ว) ยังเป็น source of truth เหมือนเดิม

**Hosting Stability (อัปเดตล่าสุด — สลับกลับมาใช้ Vercel แล้ว)** — ผู้ใช้ย้ำว่าต้องการทั้งลื่นไหล เสถียร และฟรี ไม่ใช่ฟรีอย่างเดียว:
- **ตัด Railway ออกจากตัวเลือกทั้งหมด** — ไม่ใช่ free tier จริงแล้วตั้งแต่ปี 2023 (ต้องจ่ายขั้นต่ำหลังเครดิตทดลอง $5 หมด)
- **Frontend hosting = Vercel (ตัดสินใจล่าสุด แทน Cloudflare Pages)** — ผู้ใช้ยืนยันให้ใช้ stack GitHub + Supabase + Vercel เท่านั้น ตัด Cloudflare ออกทั้งหมด (ไม่ใช้ Cloudflare Pages/Tunnel) **หมายเหตุที่ควรทราบไว้ (ยังไม่ใช่ blocker แต่เกี่ยวข้องกับหนังสือขออนุญาตที่กำลังจะร่าง)**: แผนฟรี (Hobby) ของ Vercel มีเงื่อนไขจำกัดเฉพาะการใช้งานส่วนตัว/non-commercial ตาม Terms of Service ระบบของหน่วยงานมหาวิทยาลัยอยู่ในเขตก้ำกึ่งที่อาจต้องอัปเกรดเป็นแผน Pro ($20/เดือน/ผู้ใช้) ถึงจะตรงเงื่อนไขการใช้งานเชิงองค์กรชัดเจน — ควรระบุเรื่องนี้ไว้ในหนังสือขออนุญาตเผื่อของบประมาณล่วงหน้า ไม่ต้องแก้ตอนนี้
- **Backend/DB = Supabase free tier** — schema เชิงสัมพันธ์ตรงกับที่ออกแบบไว้ แต่ **pause อัตโนมัติหลังไม่มีการใช้งาน 7 วัน** (กระทบช่วงปิดเทอมแน่นอน) → แก้โดยเขียน job แจ้งเตือน LINE (ข้อ 4.7) เป็น **Supabase Edge Function บน Supabase Cron** แทนที่จะหา cron แยก การรันทุก 1 นาทีจะแตะฐานข้อมูลเป็นการกัน pause ไปในตัว ไม่ต้องทำ keep-alive job แยกอีก
- **Firebase Firestore (Spark plan)** — ไม่มีปัญหา auto-pause เลย แต่เป็น NoSQL ต้องออกแบบ schema ใหม่จาก relational ทั้งหมด — เป็นทางเลือกสำรอง ไม่เลือกตอนนี้เพราะต้องรื้อ schema ที่ทำไปแล้วมาก
- **Code hosting/CI = GitHub** — เก็บโค้ดทั้งหมด, เชื่อมกับ Vercel สำหรับ auto-deploy เวลา push

**ฐานข้อมูล** — ตารางหลักที่ออกแบบไว้แล้ว: `users`, `students`, `face_templates`, `courses`, `semesters`, `lab_sections`, `section_enrollments`, `locations`, `schedules`, `attendance_records`, `rosters` (รายละเอียด field ทั้งหมดอยู่ในไฟล์ design doc)

**การป้องกันการโกง (ข้อ 7)** — Geofencing (ปักหมุด + รัศมีต่อห้อง ตาราง `locations`) + liveness detection กันภาพสวมรอย + device binding + face match threshold + เก็บ audit log ตำแหน่งจริงทุกครั้งที่เช็คชื่อ

**ข้อมูลชีวมาตร (Biometric/PDPA)** — เก็บเฉพาะ face embedding แบบเข้ารหัส ห้ามเก็บภาพใบหน้าดิบถ้าไม่จำเป็น ต้องขอ consent ชัดเจนก่อนลงทะเบียน มีนโยบายลบข้อมูลเมื่อพ้นสภาพนักศึกษา

**Fallback ที่ต้องมี** — offline queue เมื่อเน็ตหลุด + ช่องทางให้อาจารย์/TA เช็คชื่อมือเสมอ (กันระบบบล็อกนักศึกษาที่มาเรียนจริง)

**ระบบจองห้องแล็บ (Room Booking) — ขอบเขตแคบลงแล้ว** — ออกแบบภายในระบบนี้ทั้งหมด (ไม่ใช่ระบบภายนอก) เป็นต้นทางของตาราง `schedules` แทนการรอ sync จากระบบตารางเรียนอย่างเดียว รองรับเฉพาะ 2 ประเภทที่เกี่ยวกับการเรียนแล็บ: `class_schedule` (ตารางเรียนปกติ, แอดมินยืนยัน) และ `makeup` (ซ่อม/นัดพิเศษ) — **ตัด personal_use ออกจากขอบเขตแล้ว** การจองห้องเพื่อวัตถุประสงค์อื่นไม่เกี่ยวข้องกับ check-in เลย ควรเป็นระบบแยกต่างหาก **เหตุผลหลักของการเชื่อมระบบนี้**: รู้ว่าคาบเรียนอยู่ห้อง/ตึกไหน (`schedules.location_id`) เพื่อดึงพิกัด+รัศมีของห้องนั้นมาใช้กำหนดโซนสแกนหน้าให้แคบและตรงจุด เนื่องจากมหาวิทยาลัยมีหลายตึก ไม่ใช่แค่เรื่อง booking workflow เป็นหลัก. ระบบตารางเรียนภายนอก (ถ้ามี) ใช้แค่ให้ข้อมูลระดับหลักสูตร (วิชา/กลุ่มเรียน/อาจารย์)

**ขนาดการใช้งาน (ยืนยันแล้ว)** — ยังไม่แน่นอน อยากทดลองขนาดเล็กก่อน ยังไม่ใช่ทั้งคณะ/มหาวิทยาลัย — ทำให้ free-tier ทุกตัว (Supabase, LINE OA, Cloudflare Pages) มีพื้นที่เหลือเฟือสำหรับช่วงนี้ ไม่ต้องกังวลเรื่องโควต้าตอนนี้ ควรกลับมาคำนวณใหม่ก่อนขยายขนาด

**อุปกรณ์และสิทธิ์ตั้งค่าโซน (ยืนยันแล้ว)** — นักศึกษาส่วนใหญ่ใช้**มือถือ**เข้าระบบ (ตรงกับที่ออกแบบ PWA มือถือเป็นหลักอยู่แล้ว) และ**แอดมินเป็นผู้กำหนดโซนสแกน** (ปักหมุด+รัศมีใน `locations`) ไม่ใช่อาจารย์หรือระบบอัตโนมัติ — อัปเดตตาราง Actors ในเอกสารให้ชัดเจนแล้ว

| `real-checkin-prototype.html` | **Prototype ที่ทำงานจริง** (ไม่ใช่ mockup) — ใช้กล้อง+GPS จริงของเครื่อง (ขอความละเอียด 960×960 พร้อมแสดงค่าจริงที่ได้), คำนวณระยะทางจริงด้วย Haversine, **liveness detection ด้วย antispoof score ของ Human library** (`@vladmandic/human` — ย้ายมาจาก face-api.js ที่ archived แล้ว), **รองรับลงทะเบียนหลายคนในหน่วยความจำ + เช็คชื่อแบบไม่ล็อกอิน** (cosine similarity หาคนที่ตรงที่สุดจากรายชื่อที่ลงทะเบียนไว้เอง), คำนวณสถานะปกติ/สายจริงจากเวลา — วิดีโอครอบเป็นกรอบจัตุรัสพอดีมือถือ ไม่มี backend จริง (ข้อมูลหายเมื่อรีเฟรช) ต้องเปิดผ่าน HTTPS/localhost ไม่ใช่ file:// ถึงจะขอกล้อง/GPS ได้ **⚠️ ยังไม่ได้ทดสอบสดจริงหลัง migrate** — config/model path/ชื่อ property (`face.embedding`, `face.real`) อ้างอิงจากเอกสารที่หาได้ อาจต้องปรับหลังทดสอบจริง

## 4. ยังไม่ได้ตัดสินใจ / ต้องการข้อมูลเพิ่มเติม

- ~~ระบบตารางเรียนแล็บภายนอก...~~ → **ตอบแล้ว**: ไม่มีจริง เป็นแค่แผน ตัด Schedule Integration Layer ออก ใช้ admin CRUD ภายในระบบแทน
- แพลตฟอร์ม hosting: **ตัดสินใจแล้ว (อัปเดตล่าสุด)** = GitHub (โค้ด) + Supabase (backend/DB) + Vercel (frontend) — เหลือแค่ implement Edge Function บน Supabase Cron จริง (ดูหัวข้อ 2) และตั้งค่า GitHub repo + เชื่อม Vercel project
- นโยบาย consent และการลบข้อมูลชีวมาตรที่ต้องร่างให้สอดคล้อง PDPA ของหน่วยงาน
- ~~ใครมีสิทธิ์อนุมัติคำขอจอง...~~ → **ตอบแล้ว**: อาจารย์เจ้าของแล็บอนุมัติเองทั้ง `class_schedule` และ `makeup` ไม่ผ่านแอดมินกลาง
- ~~ถ้าห้องแล็บหลายห้องอยู่ใกล้กัน...~~ → **ตอบแล้ว**: ไม่พึ่ง GPS ล้วนๆ อีกต่อไป ใช้ QR+ตารางเรียนช่วยตัดสินแทน (ดูหัวข้อ 2) — ยังต้องทดสอบจริงหน้างานว่าตั้งรัศมีเท่าไหร่เหมาะกับแต่ละอาคาร แต่ไม่ใช่ปัญหาคอขวดแล้วเพราะมีชั้นป้องกันอื่นรองรับ
- ต้องทดสอบความเสถียรของกล้อง/GPS ผ่าน PWA บน iOS Safari จริง เทียบกับ Android Chrome ก่อนใช้งานจริง
- ~~เลือกระหว่าง MediaPipe Face Landmarker กับ face-api.js...~~ → **เจาะลึกแล้ว**: face-api.js (ทั้งต้นฉบับและ fork) ถูก archive แล้ว ไม่แนะนำใช้ต่อ เลือก **Human library** (`@vladmandic/human`, ตัวต่อยอดของ face-api.js ที่ยังดูแลอยู่) แทน — มี Face ID (liveness+matching) ในตัว รองรับโมเดล mobilefacenet สำหรับมือถือ ยังต้อง benchmark บนเครื่องจริงก่อนฟันธงสุดท้าย และยังไม่ได้ migrate prototype จาก face-api.js ไป Human จริง (ถามผู้ใช้ก่อนว่าจะให้ทำเลยไหม เพราะเป็นการเปลี่ยนโค้ดที่ทำงานอยู่แล้ว)
- **(ใหม่)** เลือก job scheduler infrastructure สำหรับแจ้งเตือน LINE (cron ธรรมดา vs queue/delayed-job)
- ~~ปริมาณข้อความ LINE OA...~~ → **ความเสี่ยงต่ำแล้ว**: ยืนยันแล้วว่าจะเริ่มทดลองขนาดเล็กก่อน (ยังไม่แน่ใจขนาดสุดท้าย) โควต้าฟรี LINE OA และ Supabase free tier มีพื้นที่เหลือเยอะสำหรับ pilot ไม่ต้องคำนวณละเอียดตอนนี้ **ควรกลับมาคำนวณใหม่ก่อนขยายเป็นทั้งคณะ/มหาวิทยาลัย**
- **(ใหม่)** ความจุ/ประเภทบัญชี Google Drive Pro ที่มี (Google One ส่วนตัว vs Google Workspace) มีผลต่อวิธีตั้งค่า service account/สิทธิ์แชร์โฟลเดอร์

## 6. หมายเหตุการใช้ไฟล์นี้

- ไฟล์นี้เก็บอยู่ในเครื่อง (sandbox) ของเซสชันนี้เท่านั้น **ไม่ได้ sync ข้ามเซสชันอัตโนมัติ**
- ให้ดาวน์โหลดเก็บไว้ และอัปโหลดกลับเข้ามาทุกครั้งที่เริ่มแชทใหม่เกี่ยวกับโปรเจกต์นี้ เพื่อให้ Claude อ่านบริบทได้ทันทีโดยไม่ต้องอธิบายซ้ำ
- ทุกครั้งที่มีการตัดสินใจใหม่ สร้างไฟล์ใหม่ หรือเปลี่ยนแผน ให้ขอให้ Claude อัปเดตไฟล์นี้ต่อท้ายหรือแก้ไขหัวข้อที่เกี่ยวข้อง
